A seat is a row, and a row is a mutex

Postgres cannot express “count of children ≤ parent.capacity” as a constraint. So the seat stops being a count and becomes a thing you take.

seat lifecycleclick a state
transition

available → locked happens inside createBooking. The row is claimed with a lock, a deadline is stamped on it, and the owning booking is recorded. 

-- the claim. this single statement is the whole race guard.
SELECT id, seat_no FROM class_seats
 WHERE class_id = $1
   AND (status = 'available'
     OR (status = 'locked' AND pending_until < now()))
 ORDER BY seat_no
 LIMIT 1
 FOR UPDATE SKIP LOCKED;
why the OR clause exists

A lapsed hold is claimable again. That is lazy expiry — it is why there is no sweeper job, and it is what makes Parent A’s late payment reachable at all.

Three invariants, all owned by the database

Application checks are advisory under concurrency. Only these three are guarantees.

I1
A class has exactly capacity seat rows.
created by generate_series(1, capacity) · kept distinct by UNIQUE (class_id, seat_no)
I2
A seat backs at most one confirmed booking.
CREATE UNIQUE INDEX … ON bookings (seat_id) WHERE status = 'CONFIRMED'
I3
At most one active booking per (student, class).
UNIQUE (student_id, class_id) WHERE status IN ('PENDING_PAYMENT','CONFIRMED')
it excludes PAYMENT_FAILED on purpose, so a parent may retry after a decline
I1 + I2 ⟹ confirmed bookings per class ≤ capacity.
No counting anywhere. Overbooking is not prevented — it is unrepresentable.

I3 has no time bound — a partial index cannot carry now(). Without this, an abandoned booking locks that child out of the class forever.
1
INSERT the booking first
A duplicate hits the I3 index and 409s before any seat is touched, so a rejected duplicate cannot burn a seat.
2

The serialisation point. Zero rows means the class is full, and the rollback undoes step 1.
3

One statement, so the CHECK constraints never see a half-written row.
4
attach seat_id to the booking, return the seat number
The parent now holds a real seat, not a promise.

Settling the payment

completePayment — where Parent A finds out.

1
lock the booking row
Unknown id → 404.
2
replay guard — if it is not PENDING_PAYMENT, change nothing
Returns already_processed. No payment attempt is written. This is what makes a double-submit safe.
3
lock the seat row
Same order as createBooking, so the two can never deadlock.
4
is the seat still mine?
status = locked and held_by_booking_id = this booking. If not, the hold lapsed and someone else took it → class_full, and no charge is attempted. Nothing to refund.
5
decline → release the seat
Booking PAYMENT_FAILED, seat back to available for the next parent.
6
success → seat booked, booking CONFIRMED
The I2 index is the last line of defence here; if it ever fires, it becomes class_full, never a 500.

SKIP LOCKED, not NOWAIT

The spec called for NOWAIT. Measured against the real database, it breaks ordinary booking.

Four parents, four seats, four claims. When only one seat is left, exactly one wins and the rest get a clean 409 class_full — a business error a parent can understand.

Every transaction aims at the same first free seat, so three parents are told the class is full while three seats sit empty. And a genuine race loss surfaces as 55P03 lock_not_available — a lock error, not a business one. That fails NFR7.
